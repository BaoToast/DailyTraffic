■ v20.33-1：每一格的車輛數，先四捨五入成整數再拿去計算

  使用者發現的：有些調查檔的儲存格裡存的其實是**小數**
  （0.36、5.5506、13.3431…），只是 Excel 的儲存格格式把它顯示成整數。

  於是**報告上看到 0 與 6，程式拿去算的卻是 0.36 與 5.5506**——
  全日車輛數會算出「27,988.79 輛」這種不存在的車，PCU 也跟著帶小數。
  從畫面上完全看不出來，因為 Excel 也顯示成整數。

  依使用者決定，一律以**畫面上看到的整數**為準。

  作法：新增 cellCount()，並且把它放在整個匯入流程**唯一讀取原始儲存格
  的地方**。舊版是五處各自寫 `Number(row[...]) || 0`，散在路段格式、
  路口左直右格式、OD（往B／往C）格式三條路徑上；補在下游只會漏掉其中一條，
  而且從畫面上看不出來。現在三條路徑都走同一支，之後的加總、尖峰小時搜尋、
  PCU 換算、全日累計全部自動吃到整數。

  「--」「－」這類代表「該轉向不存在」的字串仍然當成 0，這是舊有行為，沒有改變。

  ★ 用使用者的實際調查檔驗證（06525T2503，24 小時、儲存格帶小數）：

      舊版 v20.32   全日 24,463.3 PCU／27,988.8 輛
      本版 v20.33   全日 24,451.2 PCU／27,985 輛
      路口轉向 v2.1.30  全日 24,451.2 PCU／27,985 輛   ← 兩套系統現在一致

    另外兩份 24 小時檔（06525T2501、06525T2502）儲存格本來就是整數，
    新舊版數字完全相同。

  ★ 為什麼要做這件事：姊妹系統「路口轉向」v2.1.30 已採用同一條規則。
    不一起改的話，**同一份調查檔餵給兩套系統會得到不同的全日量**，
    而且差異小到不會有人發現。

■ v20.33-3：自訂車種不論怎麼歸類，計算都已驗證過

  這幾份調查檔的車種欄寫的是「機踏車」與「聯結車」。
  ・「機踏車」會被自動歸成機車。
  ・「聯結車」不在內建的四大車種表裡，會被當成**自訂車種**匯入，
    當量係數預設為 1，匯入流程會提示您到「車種分類與新增當量」設定。

  依使用者決定，**這個行為維持原樣**（不認得的車種寧可問您，不要自己猜；
  而且別的使用者可能想把它歸成別的車種，不一定是特種車）。

  改為用測試把「兩種做法都要算對」釘住（tests/custom-vehicle-classify.test.mjs，7 項）：

    1. 歸類回「特種車」 ≡ 原始檔本來就寫「特種車」（PCU 與輛數逐格相同）
    2. 保留成獨立車種時，用的是您自己給的係數，不是 0、也不是核心係數
    3. 不論哪一種，**車輛數合計都不變**（歸類只影響分組，不影響總量）
    4. 路段格式與路口轉向格式**兩條路徑都測**
       （路口格式走轉向係數，是完全不同的分支）
    5. 歸類回四大類的列，計算讀的是**外部的 PCU 係數**，不是建立設定當下的快照
       （測試刻意把快照寫成 999，確認算出來不會吃到它）
    6. 完全沒有設定係數時會被「尚未設定」抓出來，不會靜靜當成 0
    7. 「總量那一格」與「時段分析那一格」在每一種組合下都給出同一個答案

  ⚠️ 實務上的提醒：如果您沒有把「聯結車」指定成特種車的係數（預設是 1），
     PCU 會比路口轉向系統算出來的**低約 1%**。設定一次即可。

■ v20.32-1：合併路段會洗掉您取好的方向名稱（資料會不見，最重要的一項）

  「路段名稱管理」裡的合併功能，原本一律把**目標路段**的方向名稱，
  套用到合併之後的每一筆資料（來源與目標都算）。

  問題出在「目標路段的方向名稱」是這樣拿的：

      rows.find(r => r.directionCode === "A")?.directionName ?? "方向A"

  目標路段如果從來沒取過方向名稱，那一欄拿到的就是系統自己補上的
  「方向A」——它是一個真的字串、有長度，`??`、`||`、`if (name)`
  一律當它有值，程式分辨不出「這是使用者取的名字」還是「這是預設值」。

  結果：您在來源路段打好的「南下／北上」，
  **在按下合併的瞬間被蓋成「方向A／方向B」**，而且完全沒有提示。

  改法：目標有取過名字就以目標為準；目標只有預設值、而來源有取過名字時，
  **保留來源的名字**。確認視窗也會先寫明合併後的方向名稱會是什麼，
  按下去之前就看得到。

  ⚠️ 這和交通服務水準系統 v2.20.7 修掉的是同一類問題
     （「有沒有值」被當成「有沒有取過名字」）。三個系統我都查過了。

  ⚠️ 交通量、PCU、尖峰與車種組成的計算完全沒有變動。

  新增 tests/direction-name.test.mjs（6 項），其中 4 項已實測會在
  未修正的舊寫法下紅字。

■ v20.32-2：方向名稱被清成空白的三個地方

  （一）路段管理清單：方向名稱是空字串時 `?? "方向A"` 擋不住，
        管理畫面會顯示成一格空白。現在退回「方向A／方向B」。

  （二）匯入比對既有路段：`existingA ?? selectedMeta?.a` ——
        已匯入資料上的預設值會壓過您在路段設定裡取好的名字。
        現在以「真的取過的名字」為準。

  （三）方向名稱欄位清空後儲存：GitHub Pages 這條路徑用的是
        `String(body.directionA ?? "方向A")`，`??` 只擋 undefined，
        擋不住空字串，所以空白會被寫進資料裡。線上版用的是
        `|| "方向A"`，本來就會退回預設值。現在兩邊行為一致。
        （您的網站跑的正是 GitHub Pages 這條。）

■ v20.32-3：改路口名稱、合併路口會動到支線名稱

  路口的 A～G 是**支線**，各有自己的名字，跟路段的方向A／方向B
  是兩回事。線上版與畫面上的即時更新都會在「這是路口」時保留支線名稱，
  只有 GitHub Pages 這條路徑沒有——它照樣把支線A、支線B 換成
  方向A／方向B。當下畫面看起來正常，**重新整理之後才會發現名字沒了**。

  改法：這條路徑也改成看調查型態，是路口就不動方向名稱，與線上版一致。

■ v20.32-4：修正 eslint 設定裡一句不正確的說明

  v20.31 的註解寫「原始碼仍有 54 個錯誤與 6 個警告，已依規則性質逐項
  修正、設定或就地說明豁免」，讀起來像是全部處理完了。
  實際跑 `npm run lint` 是 **0 個錯誤、7 個警告**。

  那 7 個全是 react-hooks/exhaustive-deps，集中在 DashboardClient.tsx
  的幾個 useMemo。把 displayDirectionName 這種每次 render 都重新產生的
  函式列進相依陣列，會讓 memo 每次都失效，等於整張大表每次 render 重算。
  這是**刻意保留**的，不是還沒處理完；要動它得連同函式一起改成 useCallback，
  那是與本次修正無關的重構，依約定不在這一版做。
  註解已改成寫實際狀況，並寫明為什麼留著。
  （warning 不會讓 lint 失敗；`npm test` 仍然是綠的。）

■ v20.32-5：複查自己這一版時再抓到的四件事

  上面四項改完之後我請了一個獨立的複查再看一遍，抓到我自己改出來的問題，
  一併修掉。寫在這裡是因為其中兩件如果沒抓到，會比原本的缺陷更難查。

  （一）**合併時 A 和 B 各挑各的，會挑出兩個同名的方向。**
        我原本寫成 A 從（目標A、來源A）挑、B 從（目標B、來源B）挑。
        碰到「目標只有 B 有名字＝往南，來源 A＝往南 B＝往北」時，
        會挑出 A＝往南（來源）、B＝往南（目標）——兩個方向同名，
        篩選與 Excel 的 A／B 欄從此分不出來。**舊版反而不會**，
        因為它整組拿目標的。已改成先決定「哪一條路段的名字整組沿用」。

  （二）**判斷佔位值原本有兩套標準。** 每次載入都會跑的
        `normalizeProjectTrafficRecords` 自己用 `/^方向[AB]$/` 判斷
        （不分 A／B、也不去頭尾空白），和新的判斷會給出相反的答案。
        後果是：畫面上改好的名字，下次重新整理又被它改回去。
        已改成全系統只有一套標準。同一段裡的
        `fallbackDirection ?? defaultDirection` 也有空字串問題，一併修掉。

  （三）**離線路徑的「對齊線上版」沒有真的對齊。** 我只補了 `||`，
        漏了線上版的 `.normalize("NFKC")`。全形字（例如「南下（２）」）
        在兩邊會存成不同的字串，備份搬來搬去就對不起來。已補上，
        `targetRoadName` 也一併補（那是本來就漏的）。

  （四）**「路段格式與路口格式不可互相合併」的檢查排在確認視窗之後。**
        使用者會先看到「方向名稱將統一為…」，按下確定，才被退回。
        已移到確認視窗之前。

  另外修正我自己在 eslint 註解裡寫的說明：7 個 warning 其實分兩類，
  不是全部都是「函式沒包 useCallback」那一種。

  守門測試由 6 項增為 **9 項**，其中 **7 項**已實測會在未修正的舊寫法下紅字。

■ v20.31-4：`npm run lint` 修好了，而且以後 `npm test` 會跑它

  複查發現 lint 一直是紅的——v20.30 上實測 5687 個錯誤。

  本版：
    1. eslint 設定排除建置產物、手冊成品與測試樣本。
    2. 修掉原始碼真正的問題：9 個未使用的變數與 import、
       5 個多餘的正規表示式跳脫、2 個 any、1 個空的 catch、
       圖例文字的全形空白改成字串（那是刻意的排版字元）。
       正規表示式的改動已用 10 組樣本實測，新舊行為完全相同。
    3. 底線開頭的名稱（_projectId 這種刻意不用的佔位）不再被當成錯誤。
    4. 兩條 React Compiler 的建議規則關閉並寫明理由——本專案沒有啟用
       React Compiler，照它改要動十幾個 effect 的結構，那是與問題無關的重構。
       姊妹專案「路口轉向」早就做過同樣的取捨。

■ v20.29-1：多路口並排的調查表只讀到路口A（資料錯誤，已修正）

  使用者回報：一份四個路口並排的調查表匯入後只出現路口A，
  而且那一筆的機車數是四個路口相加（實測 57＋4＋90＋4＝155）。

  成因：舊寫法靠「車種標題重複的週期」推測每個路口佔幾欄。那份檔案的
  路口A、B 寫「大型車／特種車」，路口C、D 卻寫成「大貨車／大客車」
  （調查表的筆誤），週期不成立，於是四個路口的欄位被當成一個路口。
  最麻煩的是它不會報錯：匯入顯示成功，數字也在合理範圍。

  改法：新增 armMarkerColumns()，直接依表頭的「路口編號：路口A」標記切，
  有幾個標記就是幾個路口。找不到標記時（路段調查表）原樣走舊的週期推測。
  新增 tests/arm-split.test.mjs（4 項），已實測第 2、3 項在修正前會失敗。
  以使用者原始檔核對：路口A＝57、B＝4、C＝90、D＝4，與檔案相符。

  ⚠️ 已經匯入過的那一筆請刪掉重新匯入——升版只影響之後匯入的檔案。

■ v20.27：結論草稿存好的「條件範本」現在會跟著備份走

  使用者在結論草稿產生器存的條件範本，之前只存在該台電腦的瀏覽器裡，
  匯出的備份檔沒有收——換一台電腦匯入之後範本一個都不剩，
  而畫面只會顯示匯入成功，不會提醒少了什麼。
  本版把 conclusionTemplates 納入 exportBackup()，還原時寫回去。

  還原是**合併**不是覆蓋：同名範本以備份檔為準，本機其他名字的範本保留；
  舊版備份檔（沒有這個欄位）匯入時不會把本機既有範本清掉。
  升版前匯出的舊備份檔裡本來就沒有範本，請使用者重新匯出一份。

  新增 tests/backup-completeness.test.mjs（3 項），以清單比對釘住
  「匯出時有收、匯入時有還原、舊備份不得清空」。

■ v20.26：結論草稿的「時段」說明講清楚了
